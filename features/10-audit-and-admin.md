# 审计日志与运营后台

- 优先级：P0（关键操作）；查询体验 P1
- 当前基础：已有独立 AdminUser 和 ActiveAdmin
- 文档状态：设计草案，尚未按本文实现与验收
- 依赖：01、02、03。

## 需求

- 记录成员、权限、计费、数据删除、API Key 及运营操作，支持按时间、操作者和资源查询。
- 平台运营人员可处理租户异常，但只能在授权范围内操作。
- 高风险操作需要原因、二次验证和可追踪结果。

## 设计

- `AuditEvent(organization_id, actor_type, actor_id, action, target_type, target_id, request_id, occurred_at, redacted_changes, reason)`；系统任务也标明服务身份。
- 成功业务操作与审计同事务落库；拒绝访问等安全事件单独记录。审计不存密码、支付卡信息、完整 Token 或任意原始请求体。
- 审计对业务用户只读，禁止更新/删除入口；设置保留周期及受控归档，应用内只读不等同于底层不可篡改。
- `GET .../audit_events` 只对 owner/admin 开放；平台查询走独立 AdminUser 权限域。
- 平台角色先区分只读支持、运营和安全管理员；ActiveAdmin 的存在不等于完成角色控制。
- 不默认实现无感冒充用户；确需代操作时使用有期限、显示身份、记录原因的独立流程。

## 实现步骤

1. 建立审计事件词汇表、字段脱敏和统一写入服务。
2. 接入权限、邀请、套餐及删除等 P0 动作，补齐失败安全事件。
3. 为 ActiveAdmin 资源与自定义动作加权限；GoodJob/Flipper 管理入口限制到相应平台角色。
4. 增加有索引的筛选、导出权限及归档作业。

## 验收标准

- [ ] 所有关键成功操作存在带 actor/request_id 的审计记录。
- [ ] 普通成员不能读取审计；平台只读人员不能执行修改。
- [ ] 审计内容无秘密；事务失败不会留下虚假的成功事件。
