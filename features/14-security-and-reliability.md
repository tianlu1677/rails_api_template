# 安全、异步任务与运行保障

- 优先级：P0
- 当前基础：已有任务、监控依赖和健康接口，策略需完善
- 文档状态：设计草案，尚未按本文实现与验收
- 依赖：贯穿所有模块。

## 需求

- 认证与公开入口防滥用，故障可被发现并定位；任务失败可安全恢复。
- 备份可恢复，发布迁移可回退，敏感日志有脱敏。
- 明确服务可用性、恢复时间、可接受数据损失和告警响应人。

## 设计

- 复用 GoodJob、Sentry、New Relic、Lograge 与 `/api/v1/status`，接入依赖不代表生产配置和告警已完成。
- 按 IP、用户、组织或 API Key 对不同入口限流；多进程计数必须共享，不能使用各进程独立内存计数。`rack-attack` 已在依赖中，具体策略待落地。
- 日志关联 request_id、job_id、organization_id，脱敏凭据和个人敏感字段；监控错误率、延迟、队列积压、投递失败和对账差异。
- Job 显式传租户与资源 ID，执行前复核组织状态/必要权限；分类重试、指数退避、最大次数、死信或失败列表、人工重放。
- 数据变更与 outbox 同事务提交；分发器允许重复投递，消费者以唯一键保证幂等。
- 区分进程存活与依赖就绪检查，公开接口不暴露配置和堆栈；数据库备份加密并限制访问。
- 浏览器设置 HTTPS、Cookie 安全属性、CORS 白名单及 CSRF；Webhook 只在专用端点以签名机制替代浏览器 CSRF。
- 发布使用先扩展、回填、切换、再收紧约束的迁移流程；破坏性清理不能和首次上线捆绑。

## 实现步骤

1. 为关键路径定义告警阈值、限流规则、任务恢复和日志字段。
2. 配置监控、共享限流存储、密钥注入与轮换；接入 Job 租户上下文和 outbox。
3. 增加队列失败排查说明、支付对账排查说明和服务恢复说明。
4. 演练数据库恢复、渠道故障、任务中断及部署回滚，记录实际恢复耗时。

## 验收标准

- [ ] 多进程下限流生效，告警可到达负责人且不包含秘密。
- [ ] 同一个任务执行两次不重复扣费、计量或破坏数据。
- [ ] 数据库/邮件/支付故障有可预期降级和恢复路径。
- [ ] 恢复演练达到事先确定的 RPO/RTO，检查记录可追溯。
